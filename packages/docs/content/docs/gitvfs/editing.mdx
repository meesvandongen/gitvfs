## Staging

`writeFile`, `rm` and `rename` are synchronous: they only record a change in the buffer. Reads
see staged changes immediately, so an editor can show the state the next commit will produce.

```ts
fs.writeFile('posts/hello.md', '# Hello\n')
fs.rename('drafts/idea.md', 'posts/idea.md')
fs.rm('posts/old.md')

fs.status()
// [{ path: 'posts/hello.md', action: 'create' }, …]

fs.discard() // drop everything that is staged
```

## Committing

`commit(message)` turns every staged change into one commit and clears the buffer. It passes the
expected head commit to the host, so a commit fails with a `ConflictError` instead of
overwriting work someone pushed in the meantime.

```ts
const { sha } = await fs.commit('Publish hello post')
```

## Branches

```ts
const fs = new GitVFS({ repository, branch: 'main', writeBranch: 'content-edits' })
```

With a `writeBranch`, commits go to `writeBranch`, which is created from `branch` on the first
commit. Reads come from `writeBranch` once it exists, so edits build on earlier commits there, and
from `branch` until then. This is a good fit for review workflows where edits land in a pull
request.

The write branch does not see later changes to `branch` by itself. Merge them in with
`updateFromBase()`:

```ts
const merge = await fs.updateFromBase() // null when there was nothing to merge
```

It creates a merge commit on the host and throws a `ConflictError` when both branches changed the
same file; resolve that on the host, for example in the pull request. The GitHub provider supports
it; the GitLab provider does not yet, because GitLab only merges through merge requests.

Use `createBranch(name)` and `checkout(branch)` to manage branches directly.

## Auto-commit

```ts
const fs = new GitVFS({
  repository,
  branch: 'main',
  autoCommit: true,
  autoCommitDelay: 2000,
  commitMessage: (changes) => `Update ${changes.map((c) => c.path).join(', ')}`,
})
```

Changes are committed after the delay passes without further writes.
